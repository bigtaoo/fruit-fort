# 无尽模式那次 4.1 秒卡顿：查完的结论

一直挂在待办上的"无尽第 43 波附近 4.1 秒冻结，原因不明"。2026-11-17 查了三处，结论是**这条待办本身已经过期**，当前版本没有它的证据。

## 1. 那条记录属于已经删掉的那个应用

重建 Playgama 应用（新 id `cmwhphjpe1powlk0hhul5v0x6`）时遥测从零开始，43 波那次读数来自旧页面，和现在跑的是两份代码、两份数据。

## 2. 现在的长任务不在无尽，在 1-1 的开场

`performance_sample`，2026-11-10..17，130 条 / 16 个会话 / 13 个用户，其中 22 条带长任务记录：

- `long_task_mode`：`0`（1-1）16 条，`1` 3 条，`endless` 1 条，`9` 1 条，`3` 1 条
- `long_task_wave`：p10 1，p50 1，最大 37
- `long_task_max_ms`：最大 5164，p99 4164
- `frames_over_1000ms` 合计 12；`js_error_count`、`webgl_context_loss_count` 都是 0

也就是说，玩家真正撞上的那几秒冻结是**开场编译着色器**（warmRest 要处理的那件事），不是无尽的后半段。无尽只有孤零零一条。

## 3. 模拟这一侧是干净的

把训练全点满、用 bot 策略跑到无尽第 61 波（38843 个 tick），逐 tick 用 `process.hrtime.bigint()` 计时：**全程最慢的一个 tick 是 0.6 ms**，第 43 波本身 0.4 ms。波次计划、精英提升、多 boss、四个方向——没有一处在后期变贵。所以即便那次冻结是真的，也不在 sim 里，只可能在渲染侧。

渲染侧又排查了三条后期才首次出现的路径，都不成立：

- 画质降档重建全部程序（`quality.ts`）只在 0→1 档切阴影时发生，桌面在开局几秒内就走完，手机从第 3 档起步根本不切；
- `Horde` 的实例容量是翻倍扩容，上限有界，代价在毫秒级；
- 没被 warm 覆盖的材质只剩车厢炮弹那几个 `MeshBasicMaterial`（`wagonshots.ts`），程序变体少、编译便宜。

## 4. 下次再出现，要能当场说清是什么

长任务记录过去只说"卡了多久、第几波、多少虫"，从不说"卡在什么上"。新增 `src/platform/busy.ts`：会主动长时间占用主线程的四件事各自在动手前打一个标记——`warm`（编译着色器）、`q`（画质降档）、`save`（写存档）、`wagon`（刚选车厢，它的炮弹在第一次开火时才生成程序）——长任务带上最后一个标记和距它多久（`long_task_busy` / `long_task_busy_ms`）。`busy_ms` 远大于卡顿时长，说明只是时间上挨着，不是同一件事。

标记只跟着**本窗口最长的那次**走（`PerfSampler.longContext`），不进整窗样本：30 秒的样本没有单一的"在干什么"。
